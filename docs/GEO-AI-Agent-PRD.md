## 1. 背景与问题定义

### 1.1 行业变化：入口从「搜索列表」迁移到「AI 答案」

用户获取信息的路径正在从「关键词 → 搜索引擎 → 点开 10 个链接」迁移为「自然语言提问 → AI 直接给出结论 + 少量信源」。当客户问「XX 市哪家装修公司靠谱」「附近适合办生日宴的餐厅」时，AI 的回答本身就是一次"带货"，也可能是竞争对手的广告位。

由此产生三个结构性后果：

1. **流量入口收窄**：AI 答案只给 3~5 个信源，未进入答案的品牌获得的是 0 曝光，而不是排名靠后的低曝光。
2. **传统 SEO 手段部分失效**：排名第一不等于被 AI 引用；AI 更看重内容的事实密度、结构化程度、跨平台口径一致性以及信源权威度。
3. **企业无感知、无度量、无抓手**：绝大多数中小企业和本地商家不知道自己"在 AI 嘴里长什么样"，不知道被谁替代，也不知道该改什么。

### 1.2 目标客户的核心痛点

| 痛点 | 具体表现 | 现有替代方案的不足 |
| --- | --- | --- |
| 看不见 | 不知道 AI 如何描述自己，是否有误、是否被推荐 | 老板手动去豆包/DeepSeek 问几句，随机、不可复现、无留证 |
| 说不清 | 品牌卖点、门店、价格、资质散落在各处，口径不一致 | 官网年久失修，百科无法自建，各平台介绍各写一套 |
| 造不出 | 缺乏可持续产出"可被 AI 引用"的高质量内容的能力 | 外包写手产出 SEO 水文，AI 不引用；拍摄成本高、周期长 |
| 发不出 | 不知道去哪些媒体发才有效，投放全靠中介报价 | 通稿平台只管发不管收录，无法评估"被 AI 引用概率" |
| 测不到 | 发完之后没有闭环，不知道 ROI | 只能用 SEO 工具看网页排名，指标与 AI 答案不匹配 |

### 1.3 产品要解决的一句话问题

> 让中小企业和本地商家，用一套可量化、可执行、可复盘的流程，把"AI 说到我、说对我、优先说我"变成一件工程化的事情。

## 2. 产品定位与价值主张

### 2.1 一句话定位

GEO AI Agent 是面向本地化商家与中小企业的 **AI 可见度（GEO，Generative Engine Optimization）增长系统**，通过「AI 全景诊断 → 内容生产 → 媒体分发 → 监测复盘」四步闭环，持续提升品牌在生成式 AI 答案中的**可见度（Visibility）**、**识别度（Recognition Accuracy）**与**推荐优先级（Preference）**。

### 2.2 价值主张（按四步对应）

| 环节 | 客户获得的价值 | 可验证的交付物 |
| --- | --- | --- |
| 诊断 | 知道现状与差距：AI 怎么看我、对手怎么赢 | AI 可见度报告（AVI 分数、提及率、识别度、竞品 SoV、高频信源） |
| 资产 | 拥有唯一口径的企业知识底座与可被 AI 抓取的官网 | 结构化知识库、产品库、GEO 官网/落地页 |
| 生产 | 低成本、大批量产出"AI 愿意引用"的内容与视频 | 文章、图文、口播数字人视频、宣传片（带 AIGC 标识） |
| 分发 | 精准投到 AI 高频引用信源，而不是盲目铺量 | 选媒方案、发布回链、收录与引用监测 |
| 复盘 | 一眼看清自己和竞品的差距，并知道下一步改什么 | 工作台看板、周/月报、迭代任务清单 |

### 2.3 产品边界（明确不做）

- **不做**：黑帽刷量、伪造评价、伪造资质、批量注册账号刷问答、绕过平台风控的采集。
- **不做**：承诺"保证被 AI 引用/保证排名第一"这类不可控结果（AI 答案受模型版本、随机性、地域影响）。
- **不做**：通用 SCRM、企业官网 CMS 全家桶、通用视频剪辑软件（仅做模板化批量生产）。
- **不做**：直接对接本地生活平台的交易与核销（仅做内容与投放侧的联动与数据回传）。

### 2.4 差异化竞争力（护城河）

1. **媒体「AI 信源权重」数据库**：对 18000+ 地方官媒与 7000+ 行业大 V 建立"被 AI 引用概率"评分，选媒从"按粉丝量"升级为"按 AI 引用贡献"。
2. **口径一致性引擎**：以事实卡（Fact Card）为单一事实源，跨文章/视频/官网做冲突检测，解决 AI 最忌讳的"信息矛盾"。
3. **行业微调模型 + GEO 写作规范**：输出符合"结论前置、事实密集、Q&A 结构化"的 AEO/GEO 友好内容，而非通用大模型水文。
4. **诊断-生产-分发的数据回流**：发布数据、引用数据自动回流到选题与选媒模型，形成越用越准的闭环。

## 3. 目标用户与使用场景

### 3.1 用户角色

| 角色 | 画像 | 核心诉求 | 使用频次 |
| --- | --- | --- | --- |
| 老板 / 决策者（P1） | 40 岁上下，本地连锁或中小企业主，非技术背景 | 我要在 AI 里被推荐；钱花在哪、效果如何 | 周 1~2 次，看结论型看板与报告 |
| 市场/运营专员（P2） | 1 人市场部或代运营，身兼数职 | 少动手：内容自动生成、媒体自动推荐 | 每日 |
| 品牌/内容负责人（P3） | 中大型客户品牌部 | 口径统一、合规审核、素材授权 | 每周，做审核与发布审批 |
| 服务商/代运营（P4） | 本地营销公司、MCN、广告代理 | 多客户批量管理、白标、赚媒体差价 | 每日，跨客户切换 |
| 平台运营（内部，P5） | 我方运营/交付 | 审核内容、维护媒体库、跟进履约、处理告警 | 每日 |

### 3.2 核心 Persona 与场景故事

**Persona A：区域家装品牌「XX 装饰」市场负责人（年营收 3000 万，3 家门店）**

- 现状：投过信息流和本地生活，线索成本从 120 元涨到 380 元；发现客户开始用豆包问"本市装修公司哪家口碑好"，问出来的 5 家里没有自己。
- 使用路径：建档 → 生成 80 条本地装修 prompt → 诊断得分 12 分（满分 100），竞品 A 得 61 分 → 系统指出"AI 引用的信源 70% 是本地门户与知乎"，而自己从未在此发布 → 一键生成 20 篇攻略/对比/报价类文章 + 3 条工地实拍口播视频 → 投放到 8 家本地门户 + 12 个家居垂类账号 → 30 天后 AVI 提升至 34，官网咨询量 +41%。
- 关键诉求：省钱、看得懂、能证明有效。

**Persona B：连锁餐饮「XX 小馆」（12 家门店）**

- 现状：门店信息在 AI 里常被说错（人均价格、是否可预订、有无包间），差评旧内容被反复引用。
- 使用路径：多门店知识库（每店地址/营业时间/包间/停车/人均）→ 识别度诊断发现 7 家门店信息错误 → 生成门店级 FAQ 与本地攻略 → 分发到本地生活与地方媒体 → 监测 AI 答案中门店信息准确率从 45% 提升至 92%。
- 关键诉求：门店信息准确、负面压制、本地曝光。

**Persona C：B2B 工业配件制造商（年营收 8000 万）**

- 现状：海外客户与国内采购都用 AI 选供应商，自己在 AI 答案中"查无此人"。
- 使用路径：产品库（SKU/参数/认证）→ 行业技术问答与选型指南内容 → 行业垂媒与展会媒体分发 → 监测 AI 引用信源中"行业媒体"占比提升。
- 关键诉求：专业可信、参数准确、可被采购场景检索到。

## 4. 产品目标与成功指标

### 4.1 北极星指标（NSM）

> **月度被 AI 有效引用的品牌资产条数（Mentioned Asset Count, MAC）**
> 定义：当月 AI 探测中，出现品牌名且被正确描述的答案条数（去重后按「平台 × prompt」计）。

选择理由：同时约束"内容产出量"、"分发有效性"与"AI 实际收录"，且不可通过单一手段刷高。

### 4.2 指标体系

**客户侧（产品价值）**

| 指标 | 定义 | 首月目标 | 6 个月目标 |
| --- | --- | --- | --- |
| AVI（AI 可见度指数） | 加权提及得分，0~100（见 8.2） | 相对基线 +15 | +40 |
| BRA（品牌识别准确率） | 品牌属性描述正确率 | ≥ 70% | ≥ 90% |
| SoV（答案份额） | 品牌提及次数 / 品类总提及次数 | ≥ 15% | ≥ 30% |
| 首选推荐率 | 在决策类 prompt 中位列前 3 的比例 | ≥ 10% | ≥ 25% |
| 内容 AI 引用率 | 已发布内容被 AI 引用的条数 / 发布条数 | ≥ 8% | ≥ 20% |
| 线索增量 | 官网咨询/表单/电话/企微增量 | 可归因 ≥ 10% | ≥ 20% |

**平台侧（产品健康度）**

| 指标 | 目标 |
| --- | --- |
| 诊断报告生成成功率 | ≥ 99%，P95 时长 ≤ 30 min |
| 探测数据完整率 | ≥ 95%（平台可用性导致缺失需标注） |
| 内容合规一次通过率 | ≥ 90% |
| 媒体履约准时率 | ≥ 95%（承诺出稿时间 ±24h） |
| 客户 3 个月留存 | ≥ 75% |
| 内容人工返工率 | ≤ 15% |

### 4.3 非目标（本阶段不追求）

- 不追求覆盖全部 AI 平台（先覆盖国内 Top 8 + 海外 Top 3）。
- 不追求单条 prompt 的绝对精确（AI 答案随机，采用多次采样聚合 + 趋势判断）。
- 不追求内容"爆款率"，追求"可引用率"。

## 5. 竞品与替代方案分析

### 5.1 竞争格局

| 类别 | 代表 | 强项 | 缺口（我方机会） |
| --- | --- | --- | --- |
| 海外 GEO 监测 | Profound、Peec AI、Otterly.ai、AthenaHQ | 监测维度细、英文平台覆盖全 | 无中文平台、无媒体分发、价格高、不懂本地生活 |
| 国内 SEO/SEM 工具 | 5118、爱站、站长工具 | 关键词与排名数据成熟 | 面向网页排名，不面向 AI 答案；无内容与分发闭环 |
| 内容分发/通稿平台 | 传播易、媒介盒子、新榜有赚 | 媒体资源多、下单顺畅 | 只管发不管效果；无 AI 引用评估；无内容生产能力 |
| 数字人/视频工具 | 硅基智能、腾讯智影、剪映 | 数字人与剪辑能力强 | 孤立工具，不解决"发什么、发到哪、有没有用" |
| 代运营服务商 | 本地营销公司 | 有人情与本地资源 | 不可规模化、效果不透明、无数据系统 |
| 通用大模型 | 豆包、DeepSeek、Kimi 等 | 免费、好用 | 是"被优化对象"，不是"优化工具" |

### 5.2 竞争策略

1. **错位**：海外工具做"监测"，我们做"监测 + 生产 + 分发"的闭环，且本地化（中文平台、地方媒体、本地生活）。
2. **下沉**：把 GEO 从"大品牌专属"做成中小企业买得起的套餐（千元级起）。
3. **可验证**：所有效果都带证据链（答案原文快照 + 时间 + 平台 + 链接），解决"是不是玄学"的信任问题。

## 6. 产品架构

### 6.1 四步闭环

```
┌──────────────────────────────────────────────────────────────────────┐
│                        ① AI 全景诊断（Diagnose）                      │

└───────────────┬──────────────────────────────────────────────────────┘
                │ 差距 → 任务
┌───────────────▼──────────────────────────────────────────────────────┐
│                   ② 资产与内容生产（Build & Produce）                 │
│  知识库/产品库/事实卡 → GEO 官网 → 微调模型生成文章 → 图片/数字人/视频  │
└───────────────┬──────────────────────────────────────────────────────┘
                │ 内容 → 选媒
┌───────────────▼──────────────────────────────────────────────────────┐
│                       ③ 媒体分发（Distribute）                        │
│  18000+ 地方官媒 / 7000+ 行业 KOL / 本地生活 → 智能选媒 → 下单履约     │
└───────────────┬──────────────────────────────────────────────────────┘

```

### 6.4 关键设计原则

1. **一切可追溯**：任何结论都要能点回到"哪次探测、哪个平台、哪句原文、什么时间"。
2. **异步优先**：诊断、生成、发布均为异步任务，前端用任务中心 + 消息通知承载，避免长等待。
3. **事实唯一源**：内容生成必须引用事实卡，禁止模型自由编造品牌信息（生成前注入、生成后校验）。
4. **人工可干预**：审核、改写、驳回、二次生成全链路可用；默认"AI 生成 + 人工确认"而非全自动发布。
5. **指标可解释**：每个分数可下钻到构成项，拒绝黑箱。

### 7.1 模块 A：AI 全景诊断

**模块目标**：7 天内让客户看清"AI 眼里的我、AI 眼里的对手、差距在哪、下一步做什么"。

**用户故事**：作为市场负责人，我希望输入品牌名和所在城市后，系统自动帮我把客户会问的问题都问一遍 AI 平台，并告诉我被提到几次、说对了没有、对手为什么赢。

## 8. 核心指标与算法定义

### 8.1 提及判定规则（避免"假阳性"）

| 情形 | 判定 | 说明 |
| --- | --- | --- |
| 答案中出现品牌标准名或任一别名 | 有效提及 | 需做分词边界匹配，避免"XX 装饰"匹配到"XX 装饰城" |
| 只出现品类词/无品牌 | 未提及（记 0） | 答案列了 5 家但无我方 → 0，而非"部分命中" |
| 出现品牌但为负面/避坑名单 | 有效提及 + 负向标记 | 得分按 0.2 计，同时触发告警 |
| 出现同名不同实体 | 不计入，记"误识别" | 例如同名异地商家 |
| 答案提及但属性描述错误 | 计提及，乘以低准确度系数 | 见 8.2 |
| 平台无回答/报错 | 排除该平台分母 | 记 `null`，不得当 0 处理（会影响趋势真实性） |

### 8.2 AVI（AI 可见度指数）

\[\text{AVI} = 100 \times \frac{\sum_{i=1}^{n} w_i \cdot s_i}{\sum_{i=1}^{n} w_i}\]

其中：\(w_i\) 为第 i 条 Prompt 的权重（1/2/3，高价值决策类默认 3）；\(s_i\) 为该 Prompt 的品牌得分：

\[s_i = \frac{1}{|P_i|}\sum_{p \in P_i} \left( m_{i,p} \times a_{i,p} \right)\]

- \(P_i\)：该 Prompt 在哪些平台有有效回答（缺失平台不参与计算）。
- \(m\)（提及位次分）：未提及 = 0；提及但未推荐 = 0.4；列入推荐且排名 4+ = 0.7；列前 3 = 0.85；首位/唯一推荐 = 1.0。
- \(a\)（准确度系数）：无错误 = 1.0；信息过时/不完整 = 0.7；有明显错误（价格/地址错）= 0.4；严重错误（说已倒闭、被认定负面）= 0，并触发告警。

**分层输出**：AVI 总分、分平台 AVI、分意图 AVI（认知/比较/决策/口碑/本地）、分地域 AVI（多门店场景）。

**示例**：100 条 Prompt，其中决策型 30 条权重 3。若某决策型 Prompt 在豆包被列第 2 位且价格有误 → \(s = 0.85 \times 0.4 = 0.34\)。

### 8.3 BRA（品牌识别准确率）

\[\text{BRA} = \frac{\text{正确描述的关键属性数}}{\text{正确} + \text{错误}}\]

- 关键属性池：品牌归属/主营品类、所在城市、价格区间、核心卖点、营业/服务时间、联系方式、资质背书（按行业配置 5~8 项）。
- 属性判定由"抽取模型 + 事实卡比对"完成，低置信度进人工标注队列。
- **缺失不计入分母**（AI 没说不等于说错），但单独统计"属性覆盖率"。

### 8.4 SoV（答案份额）与首选率

- \(\text{SoV} = \dfrac{\text{品牌提及数}}{\text{品牌提及数} + \sum \text{竞品提及数}}\)，按平台/意图分别计算。
- 首选率 = 决策型 Prompt 中品牌位次 ≤ 3 的条数 / 决策型 Prompt 总条数。

### 8.5 GEOS（内容 AI 可引用性评分，0~100）

| 维度 | 分值 | 评分规则 |
| --- | --- | --- |
| 事实密度 | 20 | 每 300 字含 ≥ 1 个带数字/时间的事实句得分，线性折算 |
| 结构化程度 | 20 | 有小标题、列表、Q&A 段落、表格；Q&A 占比 ≥ 30% 满分 |
| 结论前置 | 15 | 首段 80 字内出现品牌全称 + 核心结论 |
| 实体与地域完整 | 15 | 品牌全称、别名、地域、资质首次出现均明示 |
| 数据与来源 | 20 | 关键数据带来源与时间戳（禁止无源编造） |
| 口径一致 | 10 | 与事实卡零冲突得满分，每冲突项扣 5 分 |

发布门槛：GEOS ≥ 70 且合规检查通过。

### 8.6 AIW（媒体 AI 信源权重分，0~100）

\[\text{AIW}_d = 100 \times \left( 0.6 \cdot \tilde{c}_d + 0.4 \cdot \tilde{r}_d \right)\]

- \(c_d\)：域名 d 在全部探测中被引用的次数；\(r_d\)：作为"主要来源"（首条/唯一引用）的占比。
- 两者分别做 min-max 归一化后加权。
- 维度拆分：按平台、按意图、按地域（本地媒体权重单列）。样本量 < 30 时显示"置信度低"标识。

### 8.7 双轨指标与证据分级

> 背景：客户与消费者是在 AI 的**网页版 / App** 上获取信息的，而 API 拿到的答案不含联网搜索、地理位置与产品层策略。**两者不是近似关系，而是两个不同的对象**，必须分开采、分开算、分开承诺。

#### 8.7.1 证据分级

| 级别 | channel | 来源 | 可用于 | 频率与成本 |
| --- | --- | --- | --- | --- |
| **A** | `cend` | AI 平台网页版 / App 实测（人工或插件取证，带截图） | **对外交付与合同验收** | 周/双周，每次 20–40 分钟人力 |
| B | `api_search` | 带联网搜索能力的模型 API | 日度监控与趋势 | 日更，成本低 |
| C | `api_raw` | 裸模型 API | **仅反映模型参数化记忆（“模型倾向”）** | 日更，成本极低 |
| M | `mock` | 模拟引擎 | **不可用于任何结论**，仅用于演示与回归 | — |

#### 8.7.2 两个指标，不合成一个

- `avi_cend`（**C 端可见度**）：只由 A 级记录按 8.2 公式计算；无数据时前端显示「待取证」，**绝不拿 C/M 级顶替**。
- `avi_model`（**模型倾向**）：取最近一次自动探测（B/C/M 级），页面必须带来源徽标（真实模型 API·C 级 / 模拟引擎·M 级）。
- 「主口径综合分」= 有 A 级用 A 级，否则退回模型倾向并标注来源。

#### 8.7.3 四象限（代替单一分数下结论）

以两个指标各 50 为阈值交叉：

| | 模型倾向高 | 模型倾向低 |
| --- | --- | --- |
| **C 端高** | 健康：把预算转向竞品领先场景 | **根基不稳**：靠实时抓取撑着，平台改版会掉 → 补长期资产 |
| **C 端低** | **模型认识你、检索未命中**：补高 AIW 外部信源与可引用段落（2–8 周见效） | **长期缺失**：先建口径 → 生产内容 → 集中投放 |

未取证时输出 `unknown`（“尚未取证”），不猜测。

#### 8.7.4 三条纪律（写进代码与对客话术）

1. **单轮波动只算观察，连续两轮同向才计为趋势**；AI 答案本身随机，报告需标注“观测值”。
2. **锁定变量**：每个平台固定采样模型版本、题库固定复用，否则不同轮次不可比。
3. **C/M 级不得写入对外承诺**；销售话术只引用 `avi_cend` + 截图存证。重复取证（同题×同平台）默认计为 2 次采样取均值。

#### 8.7.5 本地场景的特殊约束

本地商家最关心的「附近 XX」类问题，答案受**定位、地图与点评数据、个性化**影响，裸模型 API 完全测不到。因此取证记录必须存 `location`（提问城市），否则该类样本不得计入 `avi_cend`。

#### 8.7.6 取证工作台（引导式采集，V1 方案）

解决「取证太麻烦导致没人愿意做」：把「自己找平台、自己复制问题、自己找回表单」全部自动化，只留下「提问 + 粘贴」两步：

1. 队列按平台列出未取证问题（已取证自动消失），显示 `done/total` 与总覆盖率。
2. 点「去提问」→ **先同步复制问题到剪贴板，再新标签打开该平台网页**（顺序不能反，否则新窗口失焦导致剪贴板写入被拒）。
3. 用户登录提问、看答案 → 切回页面时自动聚焦答案框（`visibilitychange`）。
4. 粘贴 → 系统解析位次/准确度 → 入库 → 队列自动预填同平台下一条。

**边界**：跳转本身不产生数据，仍需人工回填；适合种子客户与内部巡检（一人一天可覆盖 3–5 个客户的周巡检），不适合大规模自助。平台网页地址可配（`GEO_<PLATFORM>_WEB` 覆盖），改版只改配置不改代码。剪贴板 API 需 secure context（本地 127.0.0.1 或 HTTPS）。

**重复取证**：同题同平台重复提交会计入多次采样取均值，接口返回 `duplicate` 次数，界面提示「本次作为第 N 次采样合并计算，不会重复加分」。

#### 8.8 知识库的两层：口径层与文档层

知识库不是一张表，而是两层并行，各管一件事：

| 层 | 载体 | 回答的问题 | 典型内容 |
| --- | --- | --- | --- |
| **口径层** | 事实卡（`facts`） | “对外必须怎么说、用哪个版本” | 价格区间、门店数、工期、质保、资质 |
| **文档层** | 文档 + 切片（`kb_documents` / `kb_chunks`） | “料在哪、该拿哪几段” | 产品手册、报价单、门店清单、案例、合同条款 |

**为什么不能合并**：文档里必然存在多个历史价格与过时描述，直接检索会引错数字；而只靠事实卡又只有几十条，写不出细节。所以生成时必须：检索文档拿“细节与表述”，再用事实卡覆盖/校验“数字与口径”。

**文档层实现（V1）**：上传（PDF / DOCX / XLSX / CSV / PPTX / TXT / MD，≤20MB）→ 抽取文本（带页码与标题路径）→ 切片（目标 520 字、重叠 90 字、句子边界优先）→ BM25 + 中文 bigram 建索引 → 检索返回 topK（含文档名、出处、相关度、原文）。

**已知边界**：扫描版 PDF 无文本层（需 OCR，V1.1）；`.ppt` / `.doc` 老格式需另存为新格式；PPT 事实密度低，更适合当素材而非主要知识源；当前为关键词检索（同义词召回弱），P2 接向量 + RRF 混合排序。

**图片素材（V3.0）**：支持 jpg/png/webp/gif 上传，状态记为 `image`（不抽文本、不切片），通过 `/api/kb/files/:id` 访问；生成时作为“可用图片”清单交给智能体，由它决定是否在合适位置引用。

### 8.9 官网：体检与 GEO 资产

**定位纠偏**：官网在中文 AI 引用里只占 **1.37%**，它是“事实源与结构化锚点”，不是流量入口。所以本模块**不做拖拽建站**（那是对已有官网客户的收费点陷阱），而是回答两件事：

1. **AI 现在能不能读懂你的站**（体检）
2. **不能的话补什么**（资产生成）

**体检 9 项**（全部真抓真判，不做假分数）：

| # | 检查项 | 判定依据 | 典型不通过后果 |
| --- | --- | --- | --- |
| 1 | AI 爬虫可访问 | 用 GPTBot / ClaudeBot / PerplexityBot 三个 UA 实请求首页 | CDN 拦了爬虫，AI 永远读不到 |
| 2 | robots.txt 放行 | 解析 User-agent 分组与 Disallow 规则 | 显式封禁 AI 爬虫 |
| 3 | 可见正文（不执行 JS） | `<body>` 去 script/style 后的字符数 | **SPA 站对 AI 是空壳** |
| 4 | llms.txt | 存在且非空 | AI 只能靠猜你的业务 |
| 5 | sitemap.xml | 存在且能解析 URL | 新页面发现慢 |
| 6 | 结构化数据 | 页内 JSON-LD 的 `@type` 是否含 LocalBusiness / Organization / FAQPage 等 | 无法做实体和问答摘取 |
| 7 | 标题层级 | H1 数量与 H2 数量 | 段落无法被分主题摘取 |
| 8 | 可引用段落 | ≥ 40 字的独立 `<p>` 占比 | AI 没有句子可摘 |
| 9 | 标题与描述 | title / meta description 是否存在且合理 | 摘要被系统乱编 |

**资产生成**（从事实卡与门店表，不编数据）：

- `llms.txt`：品牌 / 基本信息 / 门店清单（地址电话营业时间）/ 8 组 FAQ（按问题意图用事实拼答案，拼不出就不写）/ 引用说明
- `LocalBusiness` JSON-LD：按行业映射 `@type`（家装→HomeAndConstructionBusiness、餐饮→Restaurant…），含 priceRange / areaServed / **每家门店的 department**（地址、电话、营业时间）
- `FAQPage` JSON-LD：与 llms.txt 同源的问答，可直接被 AI 摘取
- `<head>` 片段：一行 `<link rel=alternate>` + 两段 `<script type=ld+json>`，整段粘贴即用

**已知局限**：只体检首页（不爬全站，避免被封）；不执行 JS（所以 SPA 会判为“可见正文不足”——这是真实结论，不是误判）；不支持登录后页面。

#### 8.7.5 指标按天存储带来的趋势约束

`metrics_daily` 以「品牌 + 日期」为唯一键，**同一天跑多轮探测只产生一个数据点**（后一轮覆盖前一轮）。因此：

- “趋势”的定义是**连续两个数据日同向**，不是“连续两轮”；同一天内跑十轮也看不出趋势
- 界面必须告知：数据日 < 2 时显示“至少需要 2 个不同日期才能看趋势”，而不是把单点连成线
- 轮次历史仍完整保留在 `probe_runs`（含时间戳），所以“今天跑了几轮”仍可查，只是不进入趋势

探测轮次与日指标是分开的两层，不能混为一谈。

## 9. AI 能力设计

### 9.0 智能体接入（子进程 + 事件流）

参考 `阿尔法透镜/backend/app/services/piagent.py` 的做法，但用 Node 重写为 `server/agent/piagent.js`：**不自建 agent 循环，而是把 `pi` CLI 当引擎**。

| 环节 | 做法 | 为什么 |
| --- | --- | --- |
| 启动 | `spawn(node, [cli.js, ...])`，Windows 绕过 `.ps1/.cmd` | 直接 spawn shim 在 Windows 上不可靠 |
| 传参 | 提示词写一次性文件，`-p "请读取文件 X"`，用完即删 | 避开命令行长度与转义；防上轮内容残留被读到 |
| 取过程 | `--mode json` 输出 JSON-lines，解析 `message_update.text_delta / thinking_delta / toolcall_start` | 可把思考、工具调用、正文分层展示 |
| **stdin** | **必须 `stdio: ["ignore","pipe","pipe"]`** | 保留 stdin pipe 时 pi 会等 EOF，**整个子进程卡死、零输出** |
| 工作目录 | 每品牌独立空目录 `data/agent-ws/<brandId>` | pi 启动时会扫描 cwd，放在大目录会卡住 |
| 输出 | 结束后按行重组正文，计算 GEOS，写入 `contents`（draft） | 智能体内容**不自动发布** |

**系统提示词约束**：只能引用给定事实与参考原文；禁极限词；只输出正文不说过程；不写文件、不执行命令。

**双通道并存**：模板拼装（快、可离线、零成本）+ 智能体写作（慢 15–30s、能读文档细节、有真实模型成本）。

### 9.0.1 事实回比校验（生成后）

模型会“引用”检索原文里的旧价格，也会自行外推（把区间扩大、把天数相加）。所以生成后必须程序回比：

1. 抽取正文中“数字 + 单位”组合（元/㎡、万元、天、家、人、% 等）
2. 允许集 = 所有 `active` 事实卡里的数字 + 门店数；年份与 100% 容差
3. 不允许的数字全部列出（带上下文），**不阻断入库但强制展示**，审稿人逐条确认后才发布

**提示词层面同时约束**：参考原文仅用于补充细节，数字一律以事实卡为准。实测把这两条都加上后，同一批生成从 5 个未溯源数字降到 **0**。

### 9.0.2 数据图（图文结合）

不接文生图，而是**把事实画出来**（服务端拼 SVG，零成本、可复现、爬虫可读）：

| 图型 | 数据来源 | 插入位置 |
| --- | --- | --- |
| 报价区间条形图 | 价格事实 + 竞品区间 | 首个提到“报价/价格/多少”的段落之后 |
| 工期流程图 | 工期事实 | “工期”小节 |

每张图带 `<title>` 与 `<desc>`（写清数字，供 AI 读取）、图注与数据来源行；文件名用不可猜的哈希公开寻址，供 `<img>` 直接加载。插入策略：先找对应小节标题，找不到则退到首个提及该关键词的段落，最后才放文末。

**为什么不用 AI 生图**：AI 搜索引用看的是文字与数字；生图会稀释事实密度，且在广告法语境下有“效果图误导”风险。

### 9.0.3 合规检查（发布硬拦截）

两层词库 + 行业规则，命中分两级：

| 级别 | 含义 | 处理 |
| --- | --- | --- |
| **block** | 广告法绝对化用语（最好/最佳/第一品牌/国家级/顶级/唯一/100%/零风险…） | **阻断发布**：`PATCH` 置为 published 时返回 400，并指出具体词 |
| warn | 承诺性用语（保证/绝对/免费/限时…） | 仅提示，不阻断 |

行业规则按 `brand.industry` 自动加载：医疗（疗效承诺）、教育（保过/升学率）、金融（保本/稳赚）、家装（零甲醛）。词库宁可保守：误伤改一句，漏放可能被罚。

### 9.0.4 图文导出（交付形态）

`GET /api/contents/:id/export.html?format=svg|png` 输出单文件 HTML（内联样式、图片转 data URI）：

| 版本 | 图片处理 | 体积（实测） | 用途 |
| --- | --- | --- | --- |
| 站内版（svg） | SVG 原文内联，保真 | 11.3 KB | 官网、自有站点 |
| 公众号版（png） | sharp 转 PNG，200dpi | 115 KB | 公众号 / 门户后台（不支持 SVG） |

中文渲染已实测正常（2000×417 清晰）。导出时若仍有 block 级禁用词，页面顶部会插入警告横幅。

### 9.1 模型选型

| 能力 | 方案 | 理由 |
| --- | --- | --- |
| 内容生成（文章/脚本） | 基座 Qwen 系列 / DeepSeek 私有化部署 + LoRA 微调，辅以商用闭源模型做 A/B | 成本可控、可注入行业风格、可私有化满足合规 |
| 竞品/答案解析（抽取、判定） | 小参数模型（7B~32B）+ 规则引擎 + 双模型交叉验证 | 高并发、低延迟、成本低 |
| 争议样本仲裁 | 大参数模型 LLM-as-Judge，仍不确定则进人工标注 | 保证指标可信 |
| Embedding / RAG | bge-m3 + 向量库（Milvus/PGVector） | 中文语义检索效果好 |
| 图像 | 开源 SD 系列 + 品牌 LoRA，或商用图像 API | 品牌视觉一致性 |
| 语音 | TTS 商用 API（多音色/方言），二期自研 | 快速上线 |
| 数字人 | 一期接入第三方商用数字人 API，二期自建 | 降低前期投入 |
| 合规审核 | 第三方内容安全 API + 自建规则词库（广告法/行业） | 双保险 |

### 9.2 微调策略

1. **SFT 数据集构成**：GEO 优质范文（结论前置、事实密集）× 行业深度内容 × 客户历史高转化内容 × 人工精标改写对（改写前 vs 改写后）。
2. **DPO 偏好对**：同一主题的"被 AI 引用的内容" vs "未被引用的内容"，训练模型偏好前者。
3. **数据量目标**：冷启动 5000 条 SFT + 3000 组偏好对；每月增量 10%。
4. **评测集**：固定 300 条测试题，评估事实准确率、GEOS 均分、合规通过率、可读性（人工 5 分制），每次迭代不得低于基线。
5. **发布策略**：灰度（10% 流量）→ 对比 → 全量；保留上一版本可回滚。

### 9.3 幻觉治理（关键）

| 风险 | 控制手段 |
| --- | --- |
| 编造价格/电话/地址 | 生成前注入事实卡；生成后用规则提取数字与实体，回比事实卡，不一致则重写（最多 2 次）后转人工 |
| 编造资质/奖项 | 资质字段白名单，未登记不得写入；命中则强制删除并标红 |
| 编造数据来源 | 要求引用站内已有来源或公开可查来源；无法溯源的数据禁止输出 |
| 与竞品误导性对比 | 禁止贬低性表述，只做客观参数对比，且参数需有公开来源 |
| 过时信息 | 事实卡带生效期，生成时过滤过期项 |

### 9.4 成本模型（单客户/月，粗算）

| 项目 | 用量假设 | 单位成本 | 月成本 |
| --- | --- | --- | --- |
| 全量探测 | 100 prompt × 8 平台 × 3 采样 = 2400 次 | 0.008~0.02 元/次 | 20~48 元 |

## 12. 权限矩阵

V1 实现为 4 个角色（负责人 / 编辑 / 只读 / 平台运营）；PRD 早期设想的「审核」「财务」在 V1.1 作为可配置审批流与账单角色引入。

| 操作 | 负责人 owner | 编辑 editor | 只读 viewer | 平台运营 ops |
| --- | --- | --- | --- | --- |
| 查看看板与报告 | ✓ | ✓ | ✓ | 仅订单台账 |
| 创建品牌 / 建档 | ✓ | ✓ | ✗ | ✗ |
| 新增/修改事实卡（非价格） | ✓ | ✓ | ✗ | ✗ |
| **修改价格类事实卡** | ✓ | ✗ | ✗ | ✗ |
| 运行诊断 / 生成内容 / 下单 | ✓ | ✓ | ✗ | ✗ |
| 邀请成员 / 调整角色 / 移除成员 | ✓ | ✗ | ✗ | ✗ |
| 查看操作日志 | ✓ | ✗ | ✗ | ✗ |
| 接单 / 回填发布链接 | ✗ | ✗ | ✗ | ✓（跨租户） |

实现要点：

1. **角色权重** `owner(3) > editor(2) > viewer(1)`，写操作统一走 `requireLevel("editor")`，管理类操作走 `requireLevel("owner")`。
2. **价格字段单独隔离**：属性名命中中英文价格词（价格/人均/报价/单价/price/cost/…）**或值里含金额**（¥/元/万元/元每平）时，仅负责人可增改。
3. **负责人唯一**：不能降级或移除负责人，也不能邀为负责人；不能移除自己。
4. **多租户**：所有品牌类接口经 `ownedBrand()` 校验归属，跨租户返回 404（不泄露存在性）。
5. **审计**：写请求经统一中间件记录「谁 / 何时 / 什么动作 / 对象 ID / IP」，动作已转换为业务中文（如「新增事实卡」）。

## 14. 关键业务流程

### 14.1 诊断流程（异步）

```
用户点击开始诊断
  → 校验档案完整度（< 60% 提示补全）
  → 生成 Prompt 矩阵（AI）+ 用户确认
  → 创建 ProbeTask（prompt × platform × sample=3）
  → 配额检查 → 入队 → 探测执行（重试/降级）
  → 保存快照 → 解析提及/引用/属性 → 计算 AVI/BRA/SoV
  → 生成告警 → 生成报告 + 30 天计划
  → 通知用户（站内+企微）
```

### 14.2 内容到发布流程

```
诊断缺口 → 选题（C1） → 生成内容（C2，注入事实卡）
  → GEOS 评分 + 合规校验（C3）
  → 内部审核（品牌负责人） → [代运营场景：平台复审]
  → 智能选媒（D2） → 下单（D3） → 媒体发布 → 回链
  → 入账发布台账（D4） → 3/7/15/30 天自动探测是否被引用（CiteEvidence）
  → 回流至指标与报告
```

### 14.3 告警与迭代流程

```
定时巡检（每日）→ 指标快照 → 变化检测（环比 > 30%/负面/错误）
  → 生成 Alert（分级）→ 推送 → 迭代建议引擎生成任务（E6）
  → 用户确认 → 转内容/投放任务 → 30 天后回评效果
```

### 14.4 异常场景

| 场景 | 处理 |
| --- | --- |
| AI 平台不可用/限流 | 任务延后重试，报告中标记"该平台数据缺失"，不参与分数计算 |
| 答案中检测到新竞品 | 推送到"候选竞品"列表，用户确认后加入竞品集 |
| 媒体退稿 | 订单转驳回，提示改稿重投或换媒体 |
| 发布链接失效 | 告警并标记，纳为供应商质量分；支持重发 |
| 事实卡变更 | 全量标记关联内容"待更新"，阻止新内容引用旧值 |
| 数字人授权过期 | 下线相关视频/阻止生成，提示重新授权 |

## 16. 风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| AI 平台无公开 API / 反自动化 | 探测不稳定、数据缺失 | 优先官方合作/API；多通道备份；明确"数据缺失"而非伪造；推动平台生态合作 |

| 效果不可控（发了不等于被引用） | 续费/口碑风险 | 售前不承诺排名；用基线对比 + 过程指标（收录/引用）分层承诺；合同附交付标准 |
| 模型幻觉编造品牌信息 | 客诉/法律风险 | 事实卡注入 + 生成后回比 + 白名单 + 人工审核强制 |
| 广告法/行业合规 | 罚款、稿子被删 | 多级合规规则包 + 发布前阻断 + 免责提示 |
| 数字人肖像/声音授权 | 侵权 | 授权书 + 活体校验 + 到期下线 + AIGC 标识 |
| 媒体资源虚假/掉稿 | 履约与口碑 | 准入审核 + 回链率考核 + 供应商评分 + 失效重发 |
| 大模型成本波动 | 毛利受损 | 小模型为主 + 缓存 + 配额 + 自有部署 |
| 客户认知教育成本高 | 获客贵 | 免费诊断报告作为获客钩子；行业基准报告；本地化案例库 |
| 依赖单一数字人/图像供应商 | 交付风险 | 双供应商；接口抽象；关键能力二期自建 |

## 18. 开始界面与视觉规范（Apple 风格）

> 适用范围：开始界面（Start / 首次进入、未登录态）、登录注册页、官网首页；工作台内部沿用同一套 token，但降低装饰强度。
> 原型：[prototype/index.html](../prototype/index.html)

### 18.1 为什么是 Apple 风格

本产品面向非技术背景的本地商家与中小企业主，他们的核心顾虑是"这东西靠不靠谱、我看不懂"。Apple 式设计的本质不是"好看"，而是**用极少的元素建立信任**：一屏只讲一件事、文字大而少、动效只用于引导注意力、没有任何广告感。

设计原则（按优先级排序）：

1. **一屏一主张**：首屏只回答"这是什么、对我有什么用、我现在做什么"，不堆功能列表。
2. **内容即界面**：靠字级、留白、亮度差建立层级，不靠边框、阴影、色块堆叠。
3. **黑底 + 单一强调色**：全站只用一种强调色（蓝），避免多色干扰判断。
4. **动效服务信息**：只做"进入时渐显"与"悬停微位移"，不做炫技动画，全部可关闭。
5. **数据端克制**：进入工作台后降低光晕与渐变强度，优先保证信息密度与可读性。

### 19.4 计算与探测引擎

- **AVI（7.2 / 8.2）**：`s = m × a`，m 按位次（首位 1.0 / 前 3 0.85 / 4–10 位 0.7 / 其他 0.4），a 为准确度系数；按 prompt 权重加权后 × 100。
- **识别准确率（8.3）**：只统计「被提及」的答案，未提及不计入分母（避免把「没说」算成「说错」）。
- **SoV**：我方提及数 ÷（我方 + 竞品提及数）。
- **探测适配器（P0-1 已落地）**：6 个平台各自独立配置 `GEO_<PLATFORM>_KEY / _BASE / _MODEL`，键写在 `server/.env`（服务启动时自解析，不依赖 dotenv）。配置了 KEY 的平台走真实 OpenAI 兼容调用，未配置的走确定性 mock（同一 prompt + 平台结果稳定，便于回归）。
- **调用健壮性**：单请求超时 60s；除 `auth` / `unconfigured` 外重试 2 次；错误分为 `auth / rate / http / timeout / empty / unconfigured` 六类，写入 `probe_results.err_kind`。
- **来源可追溯**：每条结果带 `source`（live / mock / error）。**失败样本不参与指标计算**（不对应「未提及」，不拉低 AVI）；全失败平台仍在分平台表里保留并标「数据缺失」。前端顶部展示「真实 / 模拟 / 失败」样本构成。
- **连通性自检**：`POST /api/providers/test` 发极小请求验证 Key 是否可用，返回耗时与模型名；前端「模型接入」抽屉内可单个测试（未配置时置灰）。
- **平台差异须如实标注**：豆包需先在方舟控制台创建推理接入点（MODEL 填 `ep-xxx`）；腾讯元宝 C 端无公开 API，当前用混元模型近似，答案风格与 C 端存在差异——该说明已在界面与配置注释中呈现。
- **指标口径规则（已落地）**：单轮波动只计观察值，**连续两轮同向才算趋势**；每平台锁定采样模型版本与题库；失败样本从分母剔除（详见 8.7.4）。
- **双轨计算（已落地）**：`avi_cend` 只由 A 级记录计算（无数据则为 `null` 并显示「待取证」），`avi_model` 取最近一次自动探测；四象限交叉出结论，未取证时输出 `unknown` 而不猜测。
- **文档检索（已落地）**：BM25（k1=1.5, b=0.75）+ 中文 bigram，零依赖零 Key、完全离线；每品牌独立内存索引，文档增删时失效重建；切片带页码与标题路径，检索结果可直接作为引用出处。向量检索与 RRF 混合排序列入 P2，接口不变。
- **智能体引擎（已落地）**：子进程调 `pi` CLI，事件归一化为 stage/thinking/tool/text/done/saved，经 SSE 推给前端；超时 180s 可中断；产物按运行前后文件快照对比。模型由本机 pi 配置决定（当前为 deepseek-v4-flash）。2026-11-09 复测：27–56s 生成 2800–4900 字，GEOS 69–76，多数含事实汇总表与数据来源行；文章专用提示词见 19.11，批量试跑样本见 `deliverables/generated-samples/`。
- **事实校验与配图（已落地）**：`checkFacts` 抽数字回比事实卡；`buildFigures/injectFigures` 生成 SVG 并按小节插入。两者都在**流结束后、入库前**执行，因此 SSE 的 `saved` 事件回传 `body`（含图最终版），否则前端预览看不到图。
- **合规与导出（已落地）**：`checkCompliance` 两层词库 + 行业规则，block 级命中写入 `contents.compliance` 并在发布时硬拦截；`md2html` 把正文转单文件 HTML，图片转 data URI，`format=png` 时用 sharp 把 SVG 转 PNG（实测中文正常，2000×417）。
- **站点体检（已落地）**：cheerio 解析 + 原生 fetch，9 项检查并行抓取（首页、robots、llms、sitemap、三个 AI 爬虫 UA），单站耗时 0.2–0.8s；可见正文只算 `<body>` 去 script/style 后的字符数，不做 JS 渲染（这是故意的：AI 爬虫也不执行 JS）。
- **监测复盘聚合（已落地）**：`/api/monitor` 一次返回双轨趋势、分平台/分意图表现、C 端取证摘要、探测轮次与**缺口清单**；样本为 0 的字段一律返回 `null`，前端不画假 0；单点改画带白边圆点。主口径额外返回 `source`（cend/model/baseline/none）与 `deltaComparable`：**口径切换时 delta 置空**，避免把“从基线切到 C 端”当成真实增长。
- **GEOS**：规则评分（事实密度 / 结构化 / 结论前置 / 实体完整 / 数据来源 / 口径一致），**六维之和严格等于总分**；「口径一致」由调用方传入，存在事实卡冲突时降为 6 分（总分同步下降），避免维度与总分对不上。

### 19.5 已验证闭环

登录 → 建档（自动生成提问）→ 事实卡新增 / 删除 / 冲突解决 → 运行 240 条探测（模拟引擎约 2 秒）→ AVI、提及率、准确率、SoV 写入 `metrics_daily` → 工作台与诊断页数字一致 → 证据抽屉可查看平台原文。

内容链路：选体裁 / 数量或指定问题 → 生成草稿（读取生效事实卡，写入 `contents`）→ 草稿提交审核 → 标记发布 → 刷新后数据保留；待审计数自动回流至工作台待办。

投放链路：按 AIW 选媒组包（前端实时算预算与均值）→ 下单写入 `orders` 并自动生成 N 条 `placements` → 标记完成同步台账状态 → 刷新后订单与台账均保留。

**人工代投闭环（P0-2 V1 方案）**：客户下单（`pending`）→ 运营在 `/ops` 接单（`claimed`，写入负责人）→ 逐条回填真实发布链接 → 全部回填后订单自动转 `published` → 客户在媒体分发页「查看链接」逐条核对。链接是交付凭证，不是状态标签。

浏览器验收结果：权限校验、路由访问、接口调用全部正常，控制台 0 error、0 个 4xx/5xx；内容生成 / 详情 / 状态流转均返回 2xx，F5 后条数不变（确认已落库）。

**双轨指标与取证实测（`scripts/smoke-evidence.mjs` + 浏览器）**：未取证时 `aviCend=null` 且四象限输出「尚未取证」（不猜测）；录入 1 条 C 端答案后自动解析位次与口径（门店数与价格与知识库不一致时 accuracy 降为 0.7）；`aviCend` 35→57 而 `aviModel` 保持 23 不被污染，四象限自动从「长期缺失」改写为「根基不稳」并给出补长期资产的下一步；诊断页顶部常驻「本页为模型口径」声明。

**取证工作台实测**：队列 40 问 × 6 平台 = 240 个样本，已取 3 条时覆盖率 1.3%；点「去提问」后正确打开对应平台并复制问题（先复制后开窗），提交后该平台计数 1/40→2/40、覆盖率 1.3%→1.7%、队列中该问题消失并自动预填下一条；重复取证返回 `duplicate=1` 且 `aviCend` 不变（不重复加分）。

**文档库与检索实测（`scripts/smoke-kb.mjs` + 浏览器）**：上传 md / csv / xlsx 三份资料分别得到 1 页 1 片（219 / 178 / 132 字），统计页与文档表数字一致（3 份 / 3 片 / 529 字）；检索「老房翻新要多少钱」命中《老房翻新说明.md·报价与工期》相关度 2.85，检索「河西店电话是多少」命中《门店清单.csv》相关度 2.71 并命中真实电话；切片抽屉可逐片核对 AI 实际会读到的文本。修掉两个真实缺陷：CSV 未按 UTF-8 读导致中文乱码（搜不到门店电话）、Markdown 短节未合并导致切片碎片化。

### 19.7 SEO 曝光率模块（增量）

**定位**：补上「传统搜索侧能不能被找到」这一层，与第 8 章的 AVI / SoV 并列，两套口径互不冒充。

**指标口径**：曝光率 = 进入搜索结果前 20 位的启用关键词数 ÷ 成功返回的关键词数 × 100；接口失败的样本从分母剔除；同日多轮只留一个日数据点；口径切换（人工录入 ↔ API 实测）时不计算涨跌。

**三路数据源**：

| 通道 | 是否真实 | 说明 |
| --- | --- | --- |
| `site` | 真抓，无需 Key | 首页 / `robots.txt` / `sitemap.xml` / 三个搜索爬虫 UA，9 项检查算「可索引性」评分，不产生排名 |
| `live` | 需配置 Key | `GEO_SEO_SEARCH_KEY` + `GEO_SEO_SEARCH_BASE`（SerpAPI 或 Bing Web Search v7），逐词查位次与 `site:` 收录数 |
| `manual` | 人工核查 / 录入 | GSC、百度搜索资源平台导出的展现量、点击、收录数，按天覆盖 |

**数据表**：`seo_keywords`（含 `enabled` 启停）、`seo_results`（逐词逐日位次与来源）、`seo_daily`（按天曝光 / 展现 / 点击快照）、`seo_scans`（站点体检历史）。

**定时扫描**：`GEO_SEO_SCAN_INTERVAL_MIN`，默认 `0` 关闭；开启后 `startSeoScheduler()` 对所有有目标网址的品牌复用 `performSeoScan()`，与手动扫描共用同一套逻辑。GEO 侧探测仍为手动触发，见 19.6。

**当前状态（2026-11-06）**：未配置搜索 Key，`live` 通道未启用；站点真抓、关键词启停、位次历史、记录增删改查与人工核查录入已可用。对 `http://159.75.21.251:3000` 实测可索引性 **41/100（4/9 通过）**，主要问题是 SPA 首屏中文正文 0 字、`robots.txt` / `sitemap.xml` 假 200、缺 H1 与 JSON-LD；公开搜索 `site:` 零命中，已录入一条人工核查基线，并在备注中标注「非逐词实测」。

**仍未做**：分引擎对比、收录 URL 明细下钻、告警、与 AVI / SoV 联动；GSC / CSV 批量导入与人工位次录入已在 19.9 落地；17.2 上线验收清单仍待逐项完成。

### 19.8 链接资产台账（增量）

**为什么**：发布地址、官网、搜索落地页与 AI 引用链接原先散落在 `placements.url`、`brands.site_url`、`seo_results.url`、`probe_results.evidence_url` 四处，且 `placements.indexed / cited` 是写死的种子值，无法回答「发到哪、还活着吗、被搜到了吗、被引用几次」。

**数据表**：`link_assets`（URL、host、类型、关联内容/媒体/订单、发布时间、来源、存活状态、HTTP 状态、收录、最后检测时间、备注；`UNIQUE(brand_id,url)`）与 `link_checks`（每次巡检的状态码、错误、耗时）。

**数据来源与口径**：

| 环节 | 来源 | 是否需要 Key |
| --- | --- | --- |
| 台账初始化 | `POST /api/links/sync` 从上述 4 处去重导入，来源标 `sync` | 否 |
| 链接存活 | `POST /api/links/check` 真发 HTTP（HEAD，不支持时降级 GET），写 `active / broken` 与巡检历史 | 否 |
| 被引用次数 | 解析 `probe_results.citations` 与 `seo_results.url`，按 host 匹配台账 | 否 |
| 收录状态 | 搜索 API 或人工回填，未检测保持 `null`，界面显示「未检测」 | 是（或人工） |

`probe_results.citations` 历史上两处写入都是空数组，现已改为从答案正文提取域名；引用统计兼容历史空数据（从 `answer` 兜底解析）。只有 `source=live` 或 C 端取证的引用计入 `citedCount`，模拟样本单列 `citedMock`，不参与效果统计。

**回填**：`GET /api/placements` 的 `indexed / cited` 改由台账与真实探测结果计算，并新增 `linkStatus`；种子数据里的 `example.com` 假链接在巡检后会被如实标记为失效，不再显示写死的「已收录 / 被引用 3 次」。

**仍未做**：定时巡检（可复用 19.7 的调度器思路）、UTM / 线索归因漏斗（E4）、转载识别、链接下线告警。

### 19.9 半自动数据通道（增量）

**定位**：不追求全自动。搜索排名与站长平台数据允许人工提供，系统负责落库、计算、趋势、来源标注与缺口提示；全自动只是省人力，不是能不能用的前提。

**人工位次录入**（`GET/POST /api/seo/positions`）：人工打开搜索引擎逐词查看位次，按日期录入；`1–20` 计入曝光，`0` = 未进前 20，留空 = 未检测（不计入分母）。结果写入 `seo_results`（`source=manual`），并由 `computeExposure()` 重算当天 `seo_daily.exposureRate`；关键词表与位次历史显示「人工核查 / 录入」，不冒充 API 实测。

**站长平台 CSV 导入**（`POST /api/seo/records/import`）：用 `papaparse` 解析 GSC / 百度搜索资源平台导出文件，列名兼容中英文（日期、展现量、点击数、点击率、平均排名、收录数、曝光率、备注）；日期兼容 `2026-11-09` / `2026/11/9` / `20261109` / `2026年11月9日`；CTR 百分号自动转小数。缺日期或无数值的坏行跳过并返回行号，单次最多 500 行。`mergeSeoDaily()` 按天**合并**写入，只覆盖 CSV 里出现的列，不会清掉人工位次算出的曝光率。

**已有人工通道（保持不变）**：C 端取证（`/evidence`，A 级证据，比裸模型 API 更权威）、人工代投回填发布链接（`/ops`）、链接台账手动标记收录与手动巡检（`/links`）、站点/SEO 手动扫描。

**口径**：人工位次与 API 实测写进同一张 `seo_results`，但 `source` 不同；`deltaComparable` 在口径切换时不计算涨跌，避免把数据源变化当成真实增长。

**零 Key 日常闭环**：人工查 8 个词位次 → 录入 → 曝光率/趋势；每周导 GSC CSV → 导入 → 展现/点击/CTR/收录；人工打开 AI 平台取证 → `/evidence` → C 端 AVI；发布后回填链接 → `/ops` → `/links` 巡检。

**仍未做**：分引擎对比、收录 URL 明细下钻、告警、与 AVI / SoV 联动；17.2 上线验收清单仍待逐项完成。

### 19.11 内容生成文章质量优化（增量）

**问题**：模板生成 `buildContent` 原为家装写死话术（拆改 / 水电 / 泥木 / 油漆、增项 500 元），对软件品牌完全不适用；事实缺失输出 `—` 占位；仅 3 组写死 Q&A；无事实回比与合规检查。智能体提示词把「门店数 0」注入，导致文章反复出现「线下门店 0 家」；要求 800–1500 字但实测 1900–2100 字，规范与产出脱节。

**改动**：

- 新增 `server/content-template.js` 纯函数 `renderArticle()`：行业无关，按已登记事实卡组织；按提问意图（认知 / 比较 / 决策 / 口碑 / 本地）切换标题与小节；事实汇总 Markdown 表格；Q&A 从本次问题与事实动态生成；缺失字段不写占位、不编造数字；数据来源注明事实卡来源
- `buildContent()` 改用该渲染器，并补上 `checkFacts()` 与 `checkCompliance()` 结果落库（与智能体通道一致）
- 新增 `articleSystemPrompt()` 文章专用提示词，与 GEOS 评分规则对齐（结论先行、`Q：`/`A：`、事实表、数据来源行、篇幅）；`runAgent` 支持按任务覆盖 system prompt，生成提问 / 事实提取等 JSON 任务仍用原提示词，避免互相干扰
- `buildPrompt()` 按意图定制结构；门店数为 0 或城市缺失时不再注入这些字段，并禁止正文出现「0 家门店」「未登记」等占位措辞
- 新增 `server/content-template.test.js` 5 个回归用例（无家装话术、无破折号占位、Q&A / 来源齐备、事实入表、意图差异、无极限词）

**实测（2026-11-09）**：

| 通道 | 字数 | GEOS | 事实回比 | 合规 | 结构 |
| --- | --- | --- | --- | --- | --- |
| 模板生成 | 1191 | 90 | 0 问题 | 0 命中 | 结论先行 + 3 节 + 事实表 + 5 组 Q&A + 来源 |
| 智能体写作 | 2867 | 75 | 见 SSE `facts` 事件 | 见 SSE `compliance` 事件 | 5 组 Q&A + 事实表 + 来源，全文无「门店 / 0 家 / 未登记」 |

**批量试跑（2026-11-09，7 篇，样本见 `deliverables/generated-samples/`）**：模板通道按 5 种提问意图各生成 1 篇，均为约 1200 字、GEOS 90、4 组 Q&A、事实回比 0 问题、合规 0 命中；智能体通道生成 2 篇，分别 4849 字 / GEOS 69 与 3950 字 / GEOS 75。其中「比较」意图那篇把「常见疑问」写成段落而非 `Q：`/`A：`，导致问答计分为 0、GEOS 下降——说明模型对格式约束仍不稳定，GEOS 规则评分对格式敏感。

**二次修正（同日）**：试跑后用户指出模板文章「只有表格，不像文章」。核查属实：5 篇各 32 行、表格 4 行，结论段完全相同，正文是「事实表 + 核验清单 + 套话问答」，靠对齐 GEOS 规则凑到 90 分。已重构 `renderArticle()`：接收 `kbSearch.buildContext()` 检索到的企业资料要点，按 5 种提问意图分别写不同的分析段落、资料引用与核对建议，表格只保留为第二节；过滤章节标题、过长句子、带单位数字与含极限词的资料句，避免事实回比与合规误伤。旧的填空式文章已从数据库删除并重新生成导出。

重构后模板文章 1179–1375 字、7 行以上成段文字、表格 4 行、事实回比 0 问题、合规 0 命中；但 GEOS 降到 65–77，说明 `scoreContent()` 的规则评分奖励「填空格式」而非可读性，不宜作为唯一质量口径，需单独改进（改动会影响历史文章分数，未擅自执行）。

**三次修正（同日，详情页只剩表格）**：用户打开内容详情发现正文只剩一张表格。根因是两处叠加：`renderArticle()` 把段落空行全部过滤，整篇成为连续单换行；前端 `Markdown` 按空行分块，块内一旦含表格行就把**整块**渲染成表格，正文被吞。已修：渲染器保留段落空行；`Markdown.tsx` 新增 `splitBlocks()` 按行把连续表格行切成独立块，且只有整块均为表格行时才渲染表格。

同时修正 `scoreContent()` 两处不合理规则：结论前置不再靠「年限」里的单字「年」误判（改为识别结论标记或带单位数字），实体完整不再只认「有限公司 / 装饰 / 门店」（补充所属行业、所在城市等），避免软件类品牌被系统性压分；新增 `server/geo-score.test.js` 4 个用例。注意评分口径调整会让历史文章在打开详情时重算分数（更公平，不是放水）；后端发布硬拦截仍只看禁用词，GEOS 只是前端提示徽标。修正后 5 篇模板文章 GEOS 83–90 全部达标、事实回比与合规均 0；无头浏览器打开详情确认结论、小节、问答、表格全部渲染，控制台 0 error。

**仍未做**：模型对篇幅与 Q&A 格式约束仍不严格（实测 2800–4900 字，个别篇 Q&A 0 组），可在保存前做确定性的格式规范化或在前端给质量提示；模板文章不自动插图（仅智能体通道有 `buildFigures`）；GEOS 仍是规则评分而非语义评分。

### 19.12 发布排期：养号阶段与知识 / GEO 穿插（增量）

**定位**：承接 `C1-3 内容日历`（P1）。在媒体分发前先排一段纯知识内容，再按比例穿插 GEO 文章；系统只生成计划与人工回填，不代发。

**必须守住的口径**：

- 养号内容不带品牌、不含数字，**永远不计入 AI 曝光指标**；只有 `kind=geo + state=published + 已回填 URL` 的条目计入效果（`summary.geoEffective`）
- 养号对平台侧账号运营可能有用，但没有证据表明能直接提升 AI 引用率；AIW 衡量的是「域名被 AI 引用的概率」，与账号年龄、发帖频率不是一回事
- 系统不调用第三方发布 API，回填链接沿用「人工代投」闭环

**规则**：`server/plan.js` 的 `buildPlanSlots()` 按渠道生成——每个渠道前 `warmupCount` 条为纯知识（`stage=warmup`），之后每 `ratio+1` 条里前 `ratio` 条知识、1 条 GEO 文章（`stage=mixed`）；GEO 条目关联真实 `contents.id`，文章不足时穿插位暂用知识内容填充并给出提示。日期按 `intervalDays` 递增，覆盖 `weeks` 周；参数均被约束在合理范围，知识选题库不含数字与绝对化用语。

**数据表**：`publish_plans`（`content_id / kind / stage / channel / planned_at / state / url / note`）。

**接口**：`GET /api/plans`（含只统计 GEO 有效条目的 `summary`）、`POST /api/plans/generate`（覆盖尚未发布的旧计划，保留已发布/已跳过）、`PATCH/DELETE /api/plans/:id`、`POST /api/plans/:id/publish`（校验 URL，写回排期并 `INSERT OR IGNORE` 进 `link_assets`，`source=plan`）。

**页面**：`/plan` —— KPI、生成表单、按周分组的时间轴表格、回填链接 / 跳过 / 删除；顶部明确标注「养号不计入指标」。

**测试**：`server/plan.test.js` 5 个用例（养号前 N 条、穿插比例与文章关联、日期与渠道隔离、参数约束、选题无数字）。

**仍未做**：第三方发布 API、审批流、按平台养号权重动态调整比例、与 AVI / AIW 的联动验证；17.2 上线验收清单仍待逐项完成。

### 19.13 Agent 工作台（增量，M2）

**定位**：把分散在 21 个页面的动作收敛成一个入口——一句话 → 意图识别 → 调已有接口 → 返回结果卡片。**不新增模型调用**，也不改变任何业务口径。

**实现**：

- `server/agent-router.js`：纯函数 `routeIntent()` 按关键词规则识别 5 类动作（produce / schedule / placement / analyze / profile），并抽取参数（体裁与提问意图、预算、养号条数、穿插比例、周数、间隔天数、品牌名/城市/行业）；匹配顺序按「越具体越优先」，识别不到具体动作时归为 `chat`（自由问答），不再直接拦成预设
- `fieldsFor()`：为每类动作给出可编辑字段（label / type / value / `fromUser`），**区分「用户句子里给的」与「默认值」**，默认项在界面上标「默认」；`needsConfirm()` 对排期这类会覆盖旧计划的动作，在参数不完整时要求先确认再执行
- `POST /api/agent/act`：按意图复用现有能力——`buildContent()` 生成文章、`applyPlanGeneration()`（从原排期路由抽出）生成排期、媒体库按 AIW 贪心组合预算、`metrics_daily + seo_daily` 汇总分析、建档参数回传向导；支持 `params` 覆盖句子解析值、`confirm` 跳过确认
- `selectAnswerHits()`：`chat` 分支先检索企业资料（BM25 取 8 条），再按「片段可用性 + 中文实词二元组覆盖」筛选——过滤章节标题、编号碎片、引用块与表格，要求至少两个实词重叠（中文二元组不足两个时降为一个），宁可少答也不拿无关段落硬凑
- `GET /api/agent/presets`：预设指令查询，页面初始即可展示
- 页面 `/agent`：对话区 + 5 个预设指令 + 结果卡片（文章 / 排期 / 投放 / 分析 / 建档 / 问答）+ **参数表单（默认值标注、改完重跑）** + 跳转对应页面的按钮

**边界（界面顶部明示）**：只识别意图并调已有接口，不额外调用模型；排期只生成计划、不代发；投放只给组合建议、不下单；问答只引用企业资料并标来源，检索不到就直说没有。

**验证**（2026-11-17）：`agent-router.test.js` 10 个单测（含字段来源、先确认、问答筛选）；后端 35/35；接口冒烟覆盖「无参数排期→待确认、改参数→生成、预算覆盖、问答命中、无命中」；无头浏览器走查确认表单（4 个字段、默认标记）、确认生成、问答来源与无命中提示，控制台 0 error。

**本轮修正（同日，用户反馈）**：初版把参数写死、识别不到就返回预设。已改为：参数摊开可改、默认值显式标注、有副作用的排期先确认；非任务输入走知识库问答，检索不到就说「没有检索到相关资料」，不再一律弹预设。

**对话能力（2026-11-18 补，用户反馈「你好」被当成检索）**：原先所有非任务输入都走知识库检索，没命中就回「没有检索到资料」，等于不会聊天。已改为三层：

1. **寒暄与能力询问**（你好 / 你能做什么 / 怎么用 / 谢谢）→ 规则直接给引导与示例，不检索，0ms
2. **企业资料命中** → 摘录原文 + 来源文件
3. **未命中** → 调用本机 `pi` 智能体回答；气泡只放一句说明，正文在卡片内并标「通用回答 · 未引用企业资料」；系统提示禁止输出思考过程，后端再清理 `I'll read that file` 这类英文工具旁白

实测：寒暄 0ms；「AgentFlow 支持哪些部署方式」0ms 命中 4 段；「公司年假怎么算」7–9s 返回通用回答，并明确说明「没有公司年假制度资料，建议查员工手册或问 HR」，不编企业事实。

**按《GEO Agent 平台技术选型与验收标准》（2026-11-18 v2）对照**：

| 验收项 | 结果 |
| --- | --- |
| 5 条预设各触发一次，均返回类型化卡片 | ✅ 文章 / 排期 / 投放 / 分析 / 建档 5 种卡片，无退化为纯文本 |
| 每次执行落 `tasks` 表（指令 / 参数 / 耗时 / 结果ID） | ✅ 新增 `agent_tasks`，页面「最近执行」可查；produce 记录 `result_id` |
| 采集类任务异步返回任务卡，其余 <30s | ⏳ 工作台暂无「采集」预设（该 tool 依赖 M3 的答案库）；其余任务实测 1–9ms |
| 报错有 toast 且任务标记失败 | ✅ 失败 toast 已验证；排期异常写 `status=failed` 与错误信息 |

**技术选型差异（沿用现有栈，未按计划换库）**：`node:sqlite` 代替 better-sqlite3、React 19 代替 18、自绘 SVG 代替 ECharts、`node:test` 代替 vitest + supertest、原生 fetch 代替 openai SDK。理由是同等能力已落地且有回归测试，换库只增加风险、不改变验收结果。
